# v1.5.0 — датасет переехал в IndexedDB

## Зачем

В v1.4.x весь реестр лежал внутри одного ключа `chrome.storage.local`.
`chrome.storage` сериализует значение целиком на каждую запись, поэтому запись
после каждой карточки стоила O(n), а весь прогон — O(n²). Кроме того, данные
хранились втройне: `batch.data`, `batch.cardCache` и `batch.finalData`.

Замер на этой машине (`node tools/bench-store.mjs 4000`):

```
rows: 4000, ~0.4 KB each
v1.4.x full-snapshot writes :   45241 ms, 6.77 GB serialised
v1.5.0 IndexedDB per record :     750 ms, 4000 rows stored

per-card cost at the end of the run:
  v1.4.x  3553 KB serialised per card, and growing
  v1.5.0  0.4 KB written per card, flat
```

60× уже на 4000 строк, и разрыв растёт: слева O(n²), справа O(n). На реальном
прогоне по 132 запросам разница на порядки больше.

## Что изменилось

### Хранилище

* Датасет переехал в IndexedDB. Базой владеет **service worker расширения**, а
  не content script: IndexedDB content script'а принадлежит origin открытой
  страницы (yandex.ru) и был бы стёрт очисткой данных сайта. Content script
  ходит в неё через `chrome.runtime.sendMessage`.
* Два хранилища: `raw` (ключ — `stableKey`, индекс по `place_id`) и `final`.
  Плюс `meta` с итогами, которые обновляются **в той же транзакции**, что и
  записи, поэтому они не могут разойтись с данными. Есть операция `recount` для
  пересчёта из самих строк.
* `cardCache` больше не существует как вторая копия данных: поиск по
  `place_id` идёт по индексу того же хранилища.
* Карточка попадает в IndexedDB в момент прочтения, до того как её посчитали.
  Падение вкладки стоит максимум одной карточки в полёте вместо всего окна
  дебаунса.
* `chrome.storage.local` остался только для управляющего состояния: статус,
  очередь запросов, счётчики, предупреждения. Это килобайты.

### Миграция

При первом запуске v1.5.0 данные v1.4.x переносятся в IndexedDB автоматически —
`batch.data`, затем незавершённый `state.data` текущего запроса, затем
`cardCache`, затем `finalData`. Порядок выбран так, чтобы строки с provenance
выигрывали. Слияние идемпотентно по ключу, поэтому прерванная миграция просто
продолжится при следующем запуске. После переноса снапшот помечается
`storageVersion: 2` и большие массивы из него удаляются.

Если миграция падает, управляющее состояние всё равно восстанавливается, а
данные остаются нетронутыми в `chrome.storage` — их можно перенести позже.

### Потоковая обработка

* `FILTER RAW → FINAL` читает RAW страницами по 500 и пишет FINAL страницами.
  Ни входной, ни выходной реестр целиком в памяти не держится.
* `EXPORT RAW` и `EXPORT FINAL` собирают CSV из кусков: `Blob` принимает массив
  строк, поэтому стомегабайтная строка больше не склеивается в памяти.

### Прочее

* Дедуп-множества (`seenUrls`, `seenPlaceIds`, `acceptedKeys`) материализуются
  один раз за окно дебаунса, а не четыре раза на карточку.
* Кнопка сброса теперь честно называется `RESET BATCH — УДАЛИТЬ RAW (N)`.
* Ключевание, слияние и дедуп вынесены в `src/shared-record.js` — один и тот же
  файл собирается и в content script, и в service worker, так что они не могут
  разойтись в понимании того, что такое одна организация.
* Отдельный `EXPORT` в панели одиночного запроса убран: реестр один, экспорт
  один.

## Инструменты

* `tools/harness.mjs` — загружает расширение в Node с реальным IndexedDB
  (`fake-indexeddb`) и настоящим путём `sendMessage`.
* `tools/smoke-test.mjs` — 47 проверок, включая миграцию с v1.4.x.
* `tools/bench-store.mjs` — замер старого и нового пути записи.
